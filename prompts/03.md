## 1. Corrigir a ordem do Write Secret Flow

O fluxo atual assina o envelope antes de anexar `previous_snapshot_hash` e incrementar `epoch`.

Isso é incorreto ou ambíguo, porque `epoch`, `previous_snapshot_hash` e AAD fazem parte do conteúdo que precisa ser assinado e autenticado.

Reordene o Write Secret Flow para que `epoch`, `previous_snapshot_hash`, `operation`, `secret_ref`, `aad`, `sealed_payload` e `wrapped_dek` estejam todos definidos antes da assinatura do Enclave e antes da countersignature do consumidor.

Use uma ordem parecida com:

1. Receive `SecretWriteRequest`.
2. Validate consumer identity.
3. Validate write policy.
4. Resolve current `trusted_chain_head`.
5. Compute next `epoch`.
6. Attach `previous_snapshot_hash`.
7. Compute `secret_ref`.
8. Build raw snapshot payload from memory state.
9. Canonicalize snapshot payload.
10. Generate per-snapshot DEK.
11. Seal canonical payload with AES-256-GCM using DEK.
12. Wrap DEK using KEK/KMS/TPM/Nitro/recipient public key.
13. Purge plaintext DEK after wrapping and sealing.
14. Build canonical envelope body containing metadata, AAD, sealed_payload and wrapped_dek.
15. Compute `snapshot_id`.
16. Sign canonical envelope body with Enclave Ed25519 key.
17. Request Consumer countersignature over the same canonical envelope body.
18. Verify both signatures.
19. Persist envelope to GitHub.
20. Attach or emit persistence receipt containing `commit_sha`.
21. Purge local temporary artifacts.
22. Emit `Secret.write.completed`.

Deixe explícito que nada deve ser assinado antes do envelope body estar completo.

## 2. Separar `commit_sha` do envelope assinado

O README atual inclui `commit_sha` dentro do envelope principal.

Isso é ambíguo porque o `commit_sha` só existe depois que o envelope já foi persistido no GitHub. Se `commit_sha` fizer parte do conteúdo assinado, há uma dependência circular:

- Para obter `commit_sha`, é preciso commitar o envelope.
- Para commitar o envelope final, seria preciso já saber o `commit_sha`.

Corrija isso separando o envelope criptográfico do recibo de persistência.

Use esta estrutura conceitual:

```json
{
  "envelope": {
    "schema_version": "lses.snapshot.v1",
    "snapshot_id": "sha256(canonical_envelope_body)",
    "project_id": "allascode",
    "environment": "prod",
    "operation": "write_secret",
    "secret_ref": "sha256(project_id + environment + secret_name)",
    "epoch": 42,
    "previous_snapshot_hash": "sha256(previous_snapshot)",
    "created_at": "2026-05-17T00:00:00Z",
    "algorithm": {
      "content_encryption": "AES-256-GCM",
      "key_wrapping": "X25519-HKDF-A256KW | KMS | TPM | NitroKMS",
      "enclave_signature": "Ed25519",
      "consumer_signature": "Ed25519"
    },
    "aad": {
      "project": "allascode",
      "environment": "prod",
      "snapshot_type": "secret_state",
      "operation": "write_secret",
      "epoch": 42,
      "previous_snapshot_hash": "sha256(previous_snapshot)"
    },
    "nonce": "base64url(random_nonce)",
    "sealed_payload": "base64url(ciphertext)",
    "auth_tag": "base64url(gcm_tag)",
    "wrapped_dek": "base64url(encrypted_data_encryption_key)",

    "enclave_public_key_id": "enclave-signing-key-2026-05",

    "consumer_public_key_id": "consumer-key-2026-05",
    "consumer_countersignature": "base64url(countersignature)"
  },
  "persistence_receipt": {
    "provider": "github",
    "repository": "owner/repo",
    "branch": "main",
    "commit_sha": "github_commit_sha",
    "committed_at": "2026-05-17T00:00:05Z"
  }
}
```

Explique:

* `snapshot_id` is computed before persistence.
* `commit_sha` is a persistence receipt, not part of the original canonical envelope body.
* The persistence receipt may be logged, audited, or signed separately if required.
* Verification of the cryptographic snapshot must not depend on GitHub’s commit SHA.

Atualize a seção “Cryptographic Envelope Format” e “GitHub Persistence Contract” com essa distinção.

## 3. Definir formalmente o que o consumidor countersigns

O README diz que o Consuming System countersigns, mas ainda precisa deixar claro exatamente o que é assinado.

Adicione uma regra formal:

Consumer countersigns the same canonical envelope body signed by the Enclave, after all security-critical fields are finalized and before persistence.

Campos que devem estar finalizados antes das duas assinaturas:

* schema_version
* snapshot_id, or canonical body used to derive it
* project_id
* environment
* operation
* secret_ref
* epoch
* previous_snapshot_hash
* created_at
* algorithm
* aad
* nonce
* sealed_payload
* auth_tag
* wrapped_dek
* dek_wrapping_key_id
* enclave_public_key_id
* consumer_public_key_id

Explique:

* O consumidor não deve assinar apenas o request original.
* O consumidor não deve assinar apenas o payload plaintext.
* O consumidor não deve assinar um envelope parcial.
* O consumidor deve assinar o envelope body já selado, com metadata e wrapped_dek.
* Isso prova que o consumidor concordou com o estado criptográfico final a ser persistido.

Adicione também um invariant:

Invariant LSES-016 — Countersignature Scope
The consumer countersignature must cover the same finalized canonical envelope body signed by the Enclave. Partial, pre-sealing or request-only countersignatures are invalid.

## 4. Separar nonce reuse de replay detection

O README atual fala que `Secret.replay.detected` é disparado em “identical or invalid nonces/signatures”.

Isso mistura conceitos diferentes.

Corrija o Event Model adicionando eventos separados:

* `Secret.nonce.reused`
* `Secret.replay.detected`
* `Secret.rollback.detected`
* `Secret.snapshot.chain.invalid`
* `Secret.signature.invalid`
* `Secret.snapshot.auth_tag.invalid`
* `Secret.snapshot.hash.invalid`

Defina cada evento:

### `Secret.nonce.reused`

Emitido quando o sistema detecta reutilização de nonce para a mesma chave ou mesmo contexto criptográfico. Isso é crítico para AES-GCM.

### `Secret.replay.detected`

Emitido quando um envelope válido ou previamente visto é reapresentado fora da sequência esperada.

### `Secret.rollback.detected`

Emitido quando `epoch <= last_accepted_epoch`.

### `Secret.snapshot.chain.invalid`

Emitido quando `previous_snapshot_hash != trusted_chain_head`.

### `Secret.signature.invalid`

Emitido quando a assinatura do Enclave ou do Consumer não verifica.

### `Secret.snapshot.auth_tag.invalid`

Emitido quando a autenticação AES-GCM falha.

### `Secret.snapshot.hash.invalid`

Emitido quando `snapshot_id` não corresponde ao hash canônico esperado.

Atualize também a tabela Failure Modes com essas categorias separadas.

## 5. Atualizar Replay and Rollback Protection

Reescreva a fórmula de aceitação para deixar claro que o envelope body finalizado é o objeto verificado.

Use algo como:

A snapshot is accepted only if:

* `snapshot_id == sha256(canonical_envelope_body)`
* `verify(enclave_signature, canonical_envelope_body)`
* `verify(consumer_countersignature, canonical_envelope_body)`
* `aes_gcm_auth_tag_valid(sealed_payload, aad, nonce, unwrapped_dek)`
* `previous_snapshot_hash == trusted_chain_head`
* `epoch > last_accepted_epoch`
* `nonce_not_reused(dek_context, nonce)`
* `schema_version is supported`
* `policy_allows(operation, consumer, secret_ref)`

Explique que:

* Signature verification detects envelope tampering.
* AES-GCM tag verification detects payload/AAD tampering.
* Epoch prevents accepting older states.
* Chain head prevents accepting old but internally consistent chains.
* Nonce tracking prevents AES-GCM misuse.
* Trust anchor is required for strong rollback protection after cold start.

## 6. Atualizar Security Invariants

Adicione estes invariantes:

Invariant LSES-016 — Countersignature Scope
The consumer countersignature must cover the same finalized canonical envelope body signed by the Enclave. Partial, pre-sealing, request-only, or plaintext-only countersignatures are invalid.

Invariant LSES-017 — Commit SHA Is Not Snapshot Identity
Git commit SHA is a persistence receipt and must not be required to compute the cryptographic snapshot identity.

Invariant LSES-018 — Security-Critical Fields Before Signing
All security-critical fields, including epoch, previous_snapshot_hash, AAD, sealed_payload, auth_tag and wrapped_dek, must be finalized before Enclave signature and Consumer countersignature.

Invariant LSES-019 — Nonce Reuse Refutation
AES-GCM nonce reuse within the same key/context must refute the operation and emit `Secret.nonce.reused`.

Invariant LSES-020 — Persistence Receipt Separation
Persistence receipts may be stored and audited, but they are separate from the canonical cryptographic envelope unless explicitly signed in a second-stage receipt signature.
