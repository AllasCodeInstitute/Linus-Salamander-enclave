Contexto da especificação:

LSES deve implementar o seguinte contrato criptográfico:

snapshot_body
→ canonical_snapshot_body
→ snapshot_id = sha256(canonical_snapshot_body)
→ signature_input = canonical({ snapshot_id, snapshot_body })
→ attestations
→ persistence_receipt

GitHub é apenas storage não confiável e pode armazenar:

{
  snapshot_body,
  snapshot_id,
  attestations,
  persistence_receipt
}

GitHub nunca deve armazenar:

- plaintext secrets
- plaintext DEKs
- private signing keys
- decrypted snapshot data
- plaintext memory dumps

O sistema usa:

- Purge-on-Write
- AES-256-GCM para sealed_payload
- DEK por snapshot
- wrapped_dek para persistir a DEK apenas encapsulada
- KEK/KMS/TPM/Nitro/recipient public key como fonte recuperável de wrapping
- Ed25519 para assinatura do Enclave
- Consumer countersignature
- snapshot_id não autorreferente
- signature_input compartilhado entre Enclave e Consumer
- RuntimeSecretHandle por padrão no readSecret
- recovery validando hash, assinaturas, chain e policy antes de unwrap/decrypt

A documentação atual já define que `snapshot_id` deve ser derivado de `canonical_snapshot_body`, que as assinaturas devem verificar contra `signature_input = canonical({ snapshot_id, snapshot_body })`, e que `persistence_receipt` não participa da identidade criptográfica. A THREAT_MODEL.md também define failure modes como nonce reuse, assinatura parcial, commit_sha usado como identidade, missing wrapped DEK e trust anchor ausente.

Corrigir o código Zig para que ele deixe de ser apenas um PoC e passe a implementar corretamente o núcleo da SPEC.

# 1. Corrigir randomness inseguro

Problema atual:

`crypto.zig` usa algo equivalente a `DefaultPrng.init(0)` dentro de `randomBytes`, fazendo com que toda chamada gere bytes previsíveis e repetidos.

Isso é crítico porque afeta:

- DEK
- nonce AES-GCM
- KEK demo
- seed Ed25519
- qualquer material criptográfico

Correção obrigatória:

- Remover PRNG determinístico para material criptográfico.
- Usar CSPRNG real do Zig, preferencialmente `std.crypto.random.bytes(out)`.
- Criar função:

```zig
pub fn randomBytes(out: []u8) void {
    std.crypto.random.bytes(out);
}
```

* Se algum teste precisar de determinismo, criar função separada somente para teste:

```zig
pub fn deterministicTestBytes(out: []u8, seed: u64) void
```

* Proibir uso de deterministicTestBytes em código de produção.

Testes obrigatórios:

* Duas chamadas consecutivas de `randomBytes` com mesmo tamanho não devem retornar o mesmo resultado.
* Nonces gerados para AES-GCM não devem repetir em um loop de teste.
* O código de produção não deve chamar `DefaultPrng.init(0)`.

# 3. Implementar canonicalization real

Problema atual:

`signature_input` é montado via string manual com `allocPrint`, o que não é canonicalização robusta.

Correção obrigatória:

Implementar:

```zig
pub fn canonicalizeSnapshotBody(
    allocator: std.mem.Allocator,
    body: SnapshotBody,
) ![]u8
```

Regras mínimas:

* A serialização deve ser determinística.
* A ordem dos campos deve ser fixa.
* Não depender de ordem de HashMap.
* Não incluir `snapshot_id`.
* Não incluir `attestations`.
* Não incluir `persistence_receipt`.
* Campos binários devem ser codificados de forma determinística, por exemplo hex ou base64url.
* A mesma entrada semântica deve gerar exatamente os mesmos bytes.

Implementar também:


E:

```zig

    allocator: std.mem.Allocator,
```


Ou seja:

* Canonicalizar `snapshot_body`.
* Incluir `snapshot_id`.
* Produzir bytes determinísticos.
* Usar exatamente os mesmos bytes para Enclave signature e Consumer countersignature.

Testes obrigatórios:

# 4. Corrigir envelope encryption e wrapped_dek

Problema atual:

A DEK é “wrapped”, mas a implementação não persiste dados suficientes para recovery. Além disso, a KEK parece ser aleatória e descartada.

Correção obrigatória:

Implementar envelope encryption recuperável.

Modelo mínimo:

```text
plaintext secret/state
→ generate per-snapshot DEK
→ AES-256-GCM encrypt payload using DEK
→ wrap DEK using recoverable KEK
→ persist sealed_payload + auth_tag + nonce + wrapped_dek + wrap metadata
→ purge plaintext DEK
```

Para ambiente de desenvolvimento, pode implementar uma `LocalDevKekProvider`, mas ela deve ser explícita e marcada como dev-only.

Exemplo:

```zig
pub const KekProvider = struct {
    key_id: []const u8,
    unwrap: fn (...) ...,
    wrap: fn (...) ...,
};
```

Ou equivalente idiomático em Zig.

O importante:

* A KEK não pode ser gerada aleatoriamente e descartada se recovery/read for esperado.
* `wrapped_dek` precisa ter metadados suficientes para unwrap.
* Se usar AES-GCM para wrap da DEK, persistir:
  * `wrapped_dek`
  * `wrap_nonce`
  * `wrap_auth_tag`
  * `dek_wrapping_key_id`
* Se usar outro esquema de key wrapping, documentar e implementar verificação correspondente.

Atualizar `SnapshotBody` para incluir, se necessário:

```zig
wrap_nonce: [12]u8,
wrap_auth_tag: [16]u8,
```

Testes obrigatórios:

* DEK plaintext nunca é serializada.
* `wrapped_dek` é obrigatório.
* unwrap com KEK errada falha.
* read/recovery consegue unwrap com KEK correta.
* mutar `wrapped_dek`, `wrap_nonce` ou `wrap_auth_tag` causa falha.
* plaintext DEK é zerada/purgada após uso quando possível.

# 6. Implementar dual attestation real

Problema atual:

O código assina com o Enclave, mas não implementa Consumer countersignature real.

Correção obrigatória:

Implementar duas identidades:

* Enclave keypair
* Consumer keypair

Fluxo:

1. Construir `snapshot_body`.
2. Canonicalizar `snapshot_body`.
3. Calcular `snapshot_id`.
4. Calcular `signature_input = canonical({ snapshot_id, snapshot_body })`.
5. Enclave assina `signature_input`.
6. Consumer countersigns o mesmo `signature_input`.
7. Persistir as duas assinaturas em `attestations`.

Implementar:

```zig
pub fn signEnclave(signature_input: []const u8, enclave_private_key: ...) ![64]u8
pub fn signConsumer(signature_input: []const u8, consumer_private_key: ...) ![64]u8
pub fn verifyAttestations(envelope: SnapshotEnvelope, keys: VerificationKeys) !void
```

Regras:

* Consumer não assina plaintext.
* Consumer não assina request original.
* Consumer não assina envelope parcial.
* Consumer assina o mesmo `signature_input` do Enclave.
* Alterar qualquer campo crítico de `snapshot_body` invalida snapshot_id e assinatura.
* Alterar `snapshot_id` invalida assinatura.
* Alterar `persistence_receipt` não invalida assinatura principal.

Testes obrigatórios:

* Enclave signature válida.
* Consumer countersignature válida.
* Consumer assinatura sobre request original deve falhar.
* Assinaturas sobre byte sequences diferentes devem falhar.
* Mutar `epoch`, `previous_snapshot_hash`, `sealed_payload`, `wrapped_dek`, `aad`, `auth_tag` ou `nonce` invalida verificação.

# 9. Implementar verifySnapshot()

```zig
pub fn verifySnapshot(
    allocator: std.mem.Allocator,
    envelope: SnapshotEnvelope,
    ctx: VerificationContext,

```

A validação deve seguir a SPEC:

```text
snapshot_id == sha256(canonical_snapshot_body)

previous_snapshot_hash == trusted_chain_head
```

2. Canonicalizar body.

4. Verificar assinaturas.

6. Validar policy.
7. Só então unwrap DEK.

Testes obrigatórios:

* Snapshot válido passa.
* Snapshot com body alterado falha.
* Snapshot com assinatura inválida falha.
* Snapshot com countersignature inválida falha.
* Snapshot antigo com epoch menor falha.
* Snapshot com previous hash errado falha.
