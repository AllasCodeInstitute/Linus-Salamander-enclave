O Linus Salamander Enclave System é um engine criptográfico de gerenciamento de segredos com filosofia “Purge-on-Write”.

O sistema:
- Não confia no GitHub para confidencialidade ou validade semântica.

## 1. Corrigir o problema das chaves efêmeras

O README atualmente sugere que snapshots são cifrados com runtime ephemeral keys, mas também diz que essas chaves são purgadas.

Isso cria uma ambiguidade grave: se a chave usada para cifrar o snapshot for purgada sem ser encapsulada, o sistema não conseguiria fazer read/recovery depois.

Corrija isso introduzindo explicitamente envelope encryption:

- O plaintext secret é cifrado com uma Data Encryption Key, chamada DEK.
- A DEK é única por snapshot.
- A DEK existe em plaintext apenas durante a operação autorizada.
- Antes do purge, a DEK é encapsulada/wrapped por uma Key Encryption Key, chamada KEK, ou por uma chave pública do Enclave/recipient.
- O GitHub armazena apenas:
  - sealed_payload
  - wrapped_dek
  - nonce
  - auth_tag
  - metadata autenticado
  - signatures
- O GitHub nunca armazena plaintext DEK.
- O recovery/read só é possível porque o Enclave consegue unwrap a DEK de forma autorizada.

Adicione ou atualize uma seção chamada:

## Envelope Encryption Model

Explique o fluxo:

Secret plaintext
→ encrypted with per-snapshot DEK
→ DEK wrapped by Enclave KEK / KMS / TPM / Nitro / recipient public key
→ sealed_payload + wrapped_dek persisted to GitHub
→ plaintext DEK purged after operation

Inclua também esta regra:

A DEK is ephemeral in plaintext form, not unrecoverable. It is persisted only as a wrapped key inside the cryptographic envelope.

## 3. Corrigir o modelo de purge local

O README diz que o LocalArtifactPurger “overwrites and deletes temporary files”.

Essa frase deve ser ajustada, porque secure overwrite não é garantido em SSDs, journaling filesystems, copy-on-write filesystems, snapshots de disco, caches do sistema operacional ou ambientes virtualizados.

Substitua por uma formulação tecnicamente precisa:

LocalArtifactPurger minimizes local persistence by deleting temporary artifacts and ensuring the implementation does not intentionally materialize plaintext secrets on disk. Secure overwrite is best-effort and filesystem-dependent.

Adicione uma seção ou nota chamada:

### Filesystem and Secure Deletion Limitations

Explique:
- LSES deve evitar criar arquivos plaintext em primeiro lugar.
- Delete/overwrite é medida de mitigação, não garantia absoluta.
- Secure deletion depende do filesystem, hardware e ambiente.
- A principal garantia vem de “do not materialize plaintext”, não de “delete depois”.

Atualize o invariant LSES-006 para refletir isso.

## 4. Separar TLS de AES-GCM

No Threat Model, ajuste a parte que fala sobre interceptação em trânsito.

Não diga que “TLS and AES-256-GCM encryption prevent interception and tampering” como se fossem a mesma camada.

Explique:

- TLS protects transport-level confidentiality and integrity.
- AES-256-GCM protects the sealed snapshot payload independently of the transport layer.
- Even if transport logs or GitHub storage are exposed, the payload remains encrypted as long as envelope keys are protected.
- TLS is required but not the sole confidentiality boundary.

## 5. Explicitar o Trust Anchor de rollback em cold start

O README fala em `trusted_chain_head` e `last_accepted_epoch`, mas precisa explicar de onde esses valores vêm quando o sistema inicia do zero.

Adicione uma seção chamada:

## Chain Head Trust Anchor

Explique que rollback protection só é forte se o sistema possui uma âncora confiável para comparar o estado remoto.

Liste opções possíveis:

- hardware monotonic counter
- TPM/Nitro/SGX-backed sealed checkpoint
- external transparency log
- signed remote chain head quorum
- operator-pinned genesis/head hash
- append-only audit log independente
- policy-defined trusted checkpoint

Explique o risco:

If LSES cold-starts with no trusted chain head, a malicious repository could present an older but internally consistent snapshot chain.

Defina comportamento:

- Se não houver trusted_chain_head, o sistema deve entrar em recovery-limited mode.
- Nesse modo, ele pode validar integridade criptográfica, mas não pode afirmar ausência completa de rollback histórico.
- Para produção, LSES deve exigir pelo menos uma fonte confiável de chain head ou checkpoint.

Atualize a seção Replay and Rollback Protection com essa limitação.

## 7. Atualizar os fluxos implementados

Atualize os fluxos Write, Read, Rotate e Recovery para incluir:

Write:
1. Gerar DEK por snapshot.
2. Cifrar payload com DEK.
3. Wrap da DEK com KEK/chave pública.
4. Purgar plaintext DEK depois do sealing.
5. Persistir apenas sealed_payload + wrapped_dek.

Read:
1. Buscar envelope.
2. Validar signatures/hash/epoch/chain.
3. Unwrap DEK dentro do Enclave.
4. Decrypt sealed_payload em memória.
5. Retornar RuntimeSecretHandle por padrão.
6. Purgar DEK plaintext e secret material após uso.

Rotate:
1. Gerar novo secret material.
2. Gerar nova DEK.
3. Criar novo wrapped_dek.
4. Incrementar epoch.
5. Encadear previous_snapshot_hash.
6. Invalidar versão anterior logicamente.

Recovery:
1. Buscar snapshots.
2. Validar chain.
3. Verificar trust anchor.
4. Entrar em recovery-limited mode se chain head confiável não existir.
5. Restaurar apenas em memória.

## 8. Atualizar invariantes

Adicione ou corrija invariantes:

Invariant LSES-011 — Wrapped DEK Required
Every persisted encrypted snapshot must include a wrapped DEK or equivalent recoverable key reference. Plaintext DEK must never be persisted.

Invariant LSES-012 — Plaintext DEK Runtime Bound
A plaintext DEK may exist only during an authorized cryptographic operation window.

Invariant LSES-013 — Trust Anchor Required for Strong Rollback Protection
Strong rollback protection requires a trusted chain head, trusted checkpoint, monotonic counter, or equivalent external trust anchor.

Invariant LSES-014 — Default Handle-Based Secret Access
Secret reads must return runtime handles by default. Plaintext export requires explicit policy authorization.

Invariant LSES-015 — Best-Effort Local Artifact Deletion
Local deletion and overwrite are best-effort mitigations. The primary invariant is that plaintext secrets must not be intentionally materialized to local disk.
