## 1. Remover autorreferência do `snapshot_id`

O README atual define:

`snapshot_id = sha256(canonical_envelope_body)`

Mas o envelope contém o próprio campo `snapshot_id`. Isso pode criar ambiguidade ou autorreferência.

Corrija a especificação para deixar explícito que o `snapshot_id` é calculado sobre o corpo canônico sem o próprio `snapshot_id` e sem assinaturas.

Use esta regra:

`snapshot_id = sha256(canonical_snapshot_body)`

Onde `canonical_snapshot_body` contém todos os campos criptograficamente relevantes, exceto:
- `snapshot_id`
- `enclave_signature`
- `consumer_countersignature`
- `persistence_receipt`

Explique claramente:

- `snapshot_id` is derived from the canonical snapshot body.
- `snapshot_id` is not included in the bytes used to compute itself.
- signatures are computed after `snapshot_id` is derived.
- `persistence_receipt` is never part of the cryptographic snapshot identity.

## 3. Definir escopo exato da assinatura

Atualize a seção de countersignature para deixar explícito:

Both Enclave signature and Consumer countersignature are computed over:

`signature_input = snapshot_id || canonical_snapshot_body`

Ou, caso prefira manter mais simples:

`signature_input = canonical({ snapshot_id, snapshot_body })`

Explique:

* Both signatures cover the same finalized snapshot identity and body.
* Neither signature covers `persistence_receipt`.
* Neither signature is computed over plaintext secrets directly.
* Neither signature is computed over partial envelopes.
* Any mutation to `snapshot_body` invalidates `snapshot_id` and signatures.
* Any mutation to `snapshot_id` invalidates signatures.
* Any mutation to `persistence_receipt` does not alter cryptographic snapshot identity, unless a second-stage receipt signature is explicitly enabled.

* `persistence_receipt` proves where it was stored, but does not define what it is.

## 5. Atualizar o Write Secret Flow

Atualize os passos relevantes do Write Secret Flow:

1. Build finalized `snapshot_body`.
2. Canonicalize `snapshot_body`.
3. Compute `snapshot_id = sha256(canonical_snapshot_body)`.
4. Compute `signature_input = canonical({ snapshot_id, snapshot_body })`.
5. Sign `signature_input` with Enclave Ed25519 key.
6. Request Consumer countersignature over the same `signature_input`.
7. Persist `{ snapshot_body, snapshot_id, attestations }` to GitHub.
8. Emit or attach `persistence_receipt`.

Deixe explícito:

* `snapshot_id` is computed before signatures.
* signatures are computed before persistence.
* `persistence_receipt` is produced after persistence.
* `commit_sha` never participates in `snapshot_id`.

16. Verify both signatures.
17. Persist to GitHub.
18. Emit or attach `persistence_receipt`.
19. Logically invalidate previous version.
20. Purge old material, plaintext DEK and local artifacts.

## 7. Atualizar Security Invariants

Adicione ou refine estes invariantes:

Invariant LSES-021 — Snapshot ID Non-Self-Reference
`snapshot_id` must be computed from `canonical_snapshot_body` and must not include itself, attestations, or persistence receipts in its hash input.

Invariant LSES-022 — Shared Signature Input
The Enclave signature and Consumer countersignature must both verify against the same `signature_input = canonical({ snapshot_id, snapshot_body })`.

Invariant LSES-023 — Persistence Receipt Exclusion
`persistence_receipt` must not affect `snapshot_id` or core snapshot signature verification unless a separate receipt-signing protocol is explicitly enabled.

Invariant LSES-024 — Rotation Uses Same Snapshot Identity Rules
Secret rotation snapshots must follow the same canonicalization, `snapshot_id`, attestation, and persistence receipt rules as write snapshots.
