Contexto documental atual:

A SPEC define o contrato criptográfico central:

snapshot_body
→ canonical_snapshot_body
→ snapshot_id = sha256(canonical_snapshot_body)
→ signature_input = canonical({ snapshot_id, snapshot_body })
→ attestations
→ persistence_receipt

GitHub é storage não confiável e pode armazenar:

{
  snapshot_body,
  snapshot_id,
  attestations,
  persistence_receipt
}

GitHub nunca deve armazenar:

- plaintext secrets
- plaintext DEKs
- private signing keys
- decrypted snapshot data
- plaintext memory dumps

A SPEC também exige que read/recovery validem hash, signatures, chain, epoch e policy antes de unwrap/decrypt. O THREAT_MODEL define failure modes como nonce reuse, invalid auth tag, invalid snapshot hash, missing wrapped DEK, chain fork, rollback attempt, missing trust anchor e request-only countersignature.

# 2. Implementar `KekProvider` recuperável

Problema atual:

A KEK é gerada randomicamente dentro do sealing/wrapping e descartada. Isso torna o `wrapped_dek` inútil para read/recovery.

Implemente uma abstração:

```zig
pub const KekProvider = struct {
    key_id: []const u8,
    ctx: *anyopaque,

    wrapFn: *const fn (
        ctx: *anyopaque,
        allocator: std.mem.Allocator,
        plaintext_dek: *const [32]u8,
        aad: []const u8,
    ) anyerror!WrappedDek,

    unwrapFn: *const fn (
        ctx: *anyopaque,
        allocator: std.mem.Allocator,
        wrapped: WrappedDek,
        aad: []const u8,
    ) anyerror![32]u8,

    pub fn wrap(
        self: KekProvider,
        allocator: std.mem.Allocator,
        plaintext_dek: *const [32]u8,
        aad: []const u8,
    ) !WrappedDek {
        return self.wrapFn(self.ctx, allocator, plaintext_dek, aad);
    }

    pub fn unwrap(
        self: KekProvider,
        allocator: std.mem.Allocator,
        wrapped: WrappedDek,
        aad: []const u8,
    ) ![32]u8 {
        return self.unwrapFn(self.ctx, allocator, wrapped, aad);
    }
};

pub const WrappedDek = struct {
    key_id: []const u8,
    wrapped_dek: []u8,
    wrap_nonce: [12]u8,
    wrap_auth_tag: [16]u8,
    algorithm: []const u8,
};
```

Crie um provider dev-only explícito:

```zig
pub const LocalDevKekProvider = struct {
    key_id: []const u8,
    kek: [32]u8,

    pub fn initFromEnvOrFixedDevKey(...) !LocalDevKekProvider {
        // DEV ONLY:
        // Preferir variável de ambiente LSES_DEV_KEK_HEX.
        // Se ausente, gerar erro em modo strict.
        // Em modo demo, permitir uma KEK fixa marcada como insegura.
    }
};
```

Regras:

* `LocalDevKekProvider` deve ser marcado como dev-only no código.
* Em produção, a interface deve permitir KMS/TPM/Nitro/recipient public key no futuro.
* A KEK deve ser recuperável entre write/read/recovery.
* O código nunca deve persistir KEK plaintext.
* `wrapped_dek`, `wrap_nonce`, `wrap_auth_tag`, `dek_wrapping_key_id` e `key_wrapping_algorithm` devem ser persistidos no `snapshot_body`.

Exemplo de uso esperado:

```zig

    "local-dev-kek-001",
    "00112233445566778899aabbccddeeff00112233445566778899aabbccddeeff",
);

const wrapped = try kek_provider.provider().wrap(
    allocator,
    &dek,
    canonical_wrap_aad,
);

const recovered_dek = try kek_provider.provider().unwrap(
    allocator,
    wrapped,
    canonical_wrap_aad,
);
```

Testes obrigatórios:

* Write com KEK A e read com KEK A funciona.
* Write com KEK A e read com KEK B falha com `WrongKek` ou `InvalidAuthTag`.
* Mutar `wrapped_dek` falha.
* Mutar `wrap_nonce` falha.
* Mutar `wrap_auth_tag` falha.
* Mutar `dek_wrapping_key_id` para key inexistente falha com `StaleKekId`.
* Plaintext DEK não aparece em JSON persistido.

const canonical_body = try canonicalizeSnapshotBody(allocator, body);
const snapshot_id = computeSnapshotId(canonical_body);
const signature_input = try canonicalizeSignatureInput(allocator, snapshot_id, body);

const enclave_sig = try signEd25519(signature_input, enclave_private_key);
const consumer_sig = try signEd25519(signature_input, consumer_private_key);

    .enclave_signature = enclave_sig,

```zig
pub fn verifyAttestations(
    allocator: std.mem.Allocator,
    body: SnapshotBody,
    snapshot_id: [32]u8,
    attestations: Attestations,
    keys: VerificationKeys,
) !void {
    const signature_input = try canonicalizeSignatureInput(allocator, snapshot_id, body);
    defer allocator.free(signature_input);

    try verifyEd25519(signature_input, attestations.enclave_signature, keys.enclave_public_key);
    try verifyEd25519(signature_input, attestations.consumer_countersignature, keys.consumer_public_key);
}
```

* Consumer assina `signature_input`, não request original.
* Enclave e Consumer assinam bytes idênticos.
* Consumer public key precisa bater com `consumer_public_key_id`.
* Enclave public key precisa bater com `enclave_public_key_id`.

Testes:

* Assinatura consumer sobre request original falha.
* Assinatura consumer com outra key falha.
* Trocar `consumer_public_key_id` sem trocar key falha.
* Mutar `snapshot_body` invalida snapshot_id/signature.
* Mutar `snapshot_id` invalida signature.
* Mutar `persistence_receipt` não invalida signature.
