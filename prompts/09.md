# 1. Corrigir ordem de persistência, trusted_chain_head e epoch

Problema atual:

O fluxo de snapshot pode atualizar `trusted_chain_head` antes de a persistência estar confirmada. Isso é perigoso: se o write/persist/Git push falhar, o runtime passa a confiar em um snapshot que não foi realmente persistido.

Regra correta:

Nunca atualize `trusted_chain_head` nem `last_accepted_epoch` antes da persistência confirmada.

O fluxo correto deve ser:

1. Criar plaintext state em memória.
2. Gerar DEK.
3. Seal payload.
4. Wrap DEK.
5. Montar `snapshot_body`.
6. Canonicalizar `snapshot_body`.
7. Calcular `snapshot_id`.
8. Calcular `signature_input`.
9. Assinar Enclave.
10. Countersign Consumer.
11. Montar envelope sem `persistence_receipt`, ou com receipt local temporário `null`.
12. Persistir envelope.
13. Obter `persistence_receipt`.
14. Opcionalmente regravar envelope com receipt, ou salvar receipt separado.
15. Só então atualizar:
   - `trusted_chain_head = snapshot_id`
   - `last_accepted_epoch = epoch`
16. Só então retornar sucesso.
17. Em caso de erro, purgar buffers sensíveis e não alterar chain head nem epoch.

Implemente um tipo explícito para resultado interno de snapshot:

```zig
pub const PendingSnapshot = struct {
    envelope: crypto.SnapshotEnvelope,
    snapshot_id: [32]u8,
    epoch: u64,
};
```

E um resultado de commit:

```zig

    envelope: crypto.SnapshotEnvelope,
    snapshot_id: [32]u8,
    epoch: u64,
    persistence_receipt: crypto.PersistenceReceipt,

```

Refatore `takeSnapshot` para  **não alterar estado global** .

# 2. Tornar `NonceRegistry` idempotente para read/recovery

Problema atual:

Se `verifySnapshot()` registra nonce toda vez que verifica um snapshot, o mesmo snapshot válido pode falhar quando lido duas vezes, porque a segunda verificação detecta o mesmo nonce como reuse.

Isso mistura dois conceitos diferentes:

* nonce reuse em novo snapshot/write
* revalidação idempotente de snapshot já aceito

A solução correta é registrar nonce com associação ao `snapshot_id`.

Crie uma estrutura parecida com:

```zig
pub const NonceUseKind = enum {
    payload,
    dek_wrap,
};

pub const NonceRecord = struct {
    snapshot_id: [32]u8,
    kind: NonceUseKind,
    nonce: [12]u8,
    context_hash: [32]u8,
};
```

O registry deve aceitar o mesmo nonce/contexto se for para o mesmo `snapshot_id` e mesmo kind, mas rejeitar se o mesmo nonce/contexto aparecer em outro snapshot.

API sugerida:

```zig
pub const NonceRegistry = struct {
    seen: std.AutoHashMap([32]u8, NonceRecord),

    pub fn checkAndRecord(
        self: *NonceRegistry,
        snapshot_id: [32]u8,
        kind: NonceUseKind,
        context: []const u8,
        nonce: [12]u8,
    ) !void {
        const key = computeNonceKey(kind, context, nonce);

        if (self.seen.get(key)) |existing| {
            if (std.mem.eql(u8, &existing.snapshot_id, &snapshot_id)) {
                // Idempotent verification of same snapshot.
                return;
            }

            return crypto.LsesError.NonceReused;
        }

        try self.seen.put(key, .{
            .snapshot_id = snapshot_id,
            .kind = kind,
            .nonce = nonce,
            .context_hash = crypto.sha256Bytes(context),
        });
    }
};
```

Função de chave:

```zig
pub fn computeNonceKey(
    kind: NonceUseKind,
    context: []const u8,
    nonce: [12]u8,
) [32]u8 {
    // sha256("LSES-NONCE-V1" || kind || context || nonce)
}
```

Regras:

* Verificar o mesmo snapshot duas vezes deve passar.
* Reutilizar nonce/contexto em snapshot diferente deve falhar.
* Payload nonce e wrap nonce devem usar domínios separados.
* Contexto deve incluir o suficiente para evitar colisão semântica.

Testes obrigatórios:

```zig

test "same payload nonce in different snapshot is rejected" {}
test "same wrap nonce in different snapshot is rejected" {}
test "payload nonce and wrap nonce use separate domains" {}
test "same nonce with different context is allowed" {}
```

Implemente:

```zig
pub fn computeSecretRef(
    project_id: []const u8,
    environment: []const u8,
    secret_name: []const u8,
) [32]u8 {
    var h = std.crypto.hash.sha2.Sha256.init(.{});
    h.update("LSES-SECRET-REF-V1");
    h.update(project_id);
    h.update("\x00");
    h.update(environment);
    h.update("\x00");
    h.update(secret_name);
    var out: [32]u8 = undefined;
    h.final(&out);
    return out;
}
```

* `secret_ref` deve mudar se `secret_name` mudar.
* `secret_ref` deve mudar se `project_id` ou `environment` mudar.
* `secret_ref` deve ser estável para mesmos inputs.

# 5. Corrigir `persistence_receipt` semantics

Problema atual:

O envelope pode estar sendo persistido com `persistence_receipt = null`. Isso é aceitável em modo local/dev temporário, mas o fluxo deve ficar explícito.

Defina duas opções válidas:

## Opção A — Receipt dentro do JSON final

1. Gravar envelope inicial sem receipt.
2. Obter receipt.
3. Regravar JSON final com `persistence_receipt`.
4. Garantir que regravar receipt não altera `snapshot_id`.

## Opção B — Receipt separado

1. Gravar envelope `{ snapshot_body, snapshot_id, attestations }`.
2. Obter receipt.
3. Gravar receipt em arquivo separado:
   * `{snapshot_id}.receipt.json`
4. `persistence_receipt` pode ser `null` no envelope principal.
5. Documentar que receipt é externo à identidade criptográfica.

Escolha uma das duas e implemente de forma consistente.

pub fn persistEnvelopeLocal(

# 7. Corrigir `readSecret`

Regras obrigatórias:

* `readSecret` deve carregar envelope.
* Deve chamar `decryptVerifiedSnapshot`.
* Se `verifySnapshot` falhar, retornar erro.
* Se unwrap falhar, retornar erro.
* Se auth tag falhar, retornar erro.
* Não retornar handle em erro.
* Retornar handle por padrão.
* Plaintext export só se:
  * `request.export_plaintext == true`
  * `ctx.policy.allow_plaintext_export == true`
  * consumer autorizado
* Se plaintext export não permitido, retornar `PlaintextExportNotAllowed`.

Exemplo:

```zig
pub fn readSecret(
    self: *Storage,
    allocator: std.mem.Allocator,
    request: SecretReadRequest,
    ctx: *crypto.VerificationContext,
) !SecretReadResult {
    const envelope = try self.loadLatestEnvelope(allocator);

    const plaintext = try crypto.decryptVerifiedSnapshot(
        allocator,
        envelope,
        ctx,
    );
    errdefer crypto.secureZero(plaintext);

    if (request.export_plaintext) {
        if (!ctx.policy.allow_plaintext_export) {
            crypto.secureZero(plaintext);
            allocator.free(plaintext);
            return crypto.LsesError.PlaintextExportNotAllowed;
        }

        return .{ .plaintext = plaintext };
    }

    const handle = try self.runtime_store.insert(
        allocator,
        plaintext,
        .{ .ttl_seconds = 60 },
    );

    crypto.secureZero(plaintext);
    allocator.free(plaintext);

    return .{ .handle = handle };
}
```

# 13. Critérios de aceitação
