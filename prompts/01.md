Contexto atual do projeto:

O Linus Salamander Enclave System é um engine criptográfico de gerenciamento de segredos inspirado em Infisical, mas desenhado para ambientes com zero persistência local. O sistema opera com a filosofia “Purge-on-Write”: segredos podem existir apenas em memória protegida durante runtime, nunca em disco local em plaintext nem em formato recuperável. A persistência autoritativa ocorre remotamente por meio de snapshots criptografados, versionados e enviados para GitHub.

A implementação atual possui estes pilares:

1. Zero-Knowledge Enclave Storage
- Segredos residem apenas no espaço de memória do Enclave durante runtime.
- Nenhum segredo plaintext deve ser persistido localmente.
- O estado persistente autoritativo é um repositório remoto versionado.
- Após qualquer operação que gere artefato temporário, o sistema executa purge local.

2. Signal-Pattern Cryptography
- Cada mudança de estado gera um snapshot criptográfico.
- O payload é selado com AES-256-GCM usando chaves efêmeras.
- Cada snapshot é assinado pelo Enclave Service usando Ed25519.
- O snapshot também deve ser countersigned pelo Consuming System.
- A ideia é aproximar cada snapshot de um “cryptographic tick”, inspirado em Double Ratchet/Signal-like progression.

3. GitHub Persistence & Versioning
- A cada alteração:
  1. O estado atual em memória é convertido em snapshot.
  2. O snapshot é selado criptograficamente.
  3. O envelope criptográfico é commitado e enviado para GitHub.
  4. Artefatos locais são purgados imediatamente.

4. Objetivo de segurança
- Reduzir exposição forense local.
- Impedir recuperação de segredos via disco local.
- Tornar alterações auditáveis via histórico versionado.
- Separar confiança entre Policy/Enclave Engine e Storage Provider.
- Evitar que GitHub sozinho consiga revelar, alterar ou reproduzir segredos válidos.

## 10. Security Invariants
Adicione invariantes numeradas.

Exemplo:

Invariant LSES-001 — No Local Plaintext Persistence
No plaintext secret may be written to local disk at any point in the lifecycle.

Invariant LSES-002 — Persisted State Must Be Sealed
Every persisted snapshot must contain encrypted payload, authenticated metadata, enclave signature and consumer countersignature.

Invariant LSES-003 — Dual Attestation Required
A snapshot is invalid unless both Enclave Service and Consuming System signatures verify against the canonical envelope.

Invariant LSES-004 — Monotonic Epoch
A snapshot with epoch lower than or equal to the last accepted epoch must be rejected.

Invariant LSES-005 — Chain Continuity
A snapshot must reference the currently trusted previous snapshot hash.

Invariant LSES-006 — Purge After Persistence
After a successful write, every temporary local artifact must be purged.

Invariant LSES-007 — No GitHub Trust Assumption
GitHub must never be required to preserve confidentiality or semantic validity.

Invariant LSES-008 — Canonical Signature Input
All signed data must be canonicalized before signing.

Invariant LSES-009 — Runtime Exposure Bound
Plaintext secret material may exist only inside an authorized runtime operation window.

Invariant LSES-010 — Refuse on Verification Failure
Any failure in signature, hash, epoch, schema or policy validation must refute the operation.
